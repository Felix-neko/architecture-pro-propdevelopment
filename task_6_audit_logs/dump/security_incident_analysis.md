# Анализ инцидента безопасности Kubernetes: Аудит-логи и симуляция атаки

## Обзор инцидента

Данный анализ основан на аудит-логах Kubernetes, собранных во время выполнения скрипта симуляции инцидента безопасности (`simulate_incident.sh`). Скрипт моделирует типичную цепочку атаки в кластере Kubernetes, включая создание вредоносных ресурсов, попытки несанкционированного доступа к секретам, создание привилегированных подов и эскалацию привилегий.

## Структура анализа

1. **Критические события безопасности** - события, представляющие прямую угрозу
2. **Подозрительные операции** - операции, требующие дополнительного внимания
3. **Корреляция с действиями скрипта** - сопоставление событий в логах с шагами атаки
4. **Рекомендации по безопасности** - меры по предотвращению подобных инцидентов

## 1. КРИТИЧЕСКИЕ СОБЫТИЯ БЕЗОПАСНОСТИ

### 1.1 Создание подозрительного namespace "secure-ops"

**Событие в аудит-логах:**
```json
{
  "kind": "Event",
  "verb": "create",
  "user": {"username": "minikube-user", "groups": ["system:masters"]},
  "objectRef": {"resource": "namespaces", "name": "secure-ops"},
  "responseStatus": {"code": 201}
}
```

**Анализ:**
- ✅ **РАЗРЕШЕНО**: Пользователь `minikube-user` с правами `system:masters` создал namespace
- 🚨 **КРИТИЧНО**: Название "secure-ops" может маскировать вредоносную активность под видом операций безопасности
- 📍 **Корреляция**: Соответствует шагу 1 скрипта `kubectl create namespace secure-ops`

### 1.2 Создание service account "monitoring" для маскировки

**Событие в аудит-логах:**
```json
{
  "verb": "create",
  "objectRef": {"resource": "serviceaccounts", "namespace": "secure-ops", "name": "monitoring"},
  "responseStatus": {"code": 201}
}
```

**Анализ:**
- ✅ **РАЗРЕШЕНО**: Создание service account выполнено успешно
- 🚨 **ПОДОЗРИТЕЛЬНО**: Имя "monitoring" используется для маскировки под легитимные системы мониторинга
- 📍 **Корреляция**: Шаг 2 скрипта - создание SA для последующих операций

### 1.3 Развертывание "attacker-pod" - вредоносного пода

**Событие создания:**
```json
{
  "verb": "create",
  "objectRef": {"resource": "pods", "namespace": "secure-ops", "name": "attacker-pod"},
  "requestObject": {
    "spec": {
      "serviceAccountName": "monitoring",
      "containers": [{"image": "alpine", "command": ["sleep", "3600"]}]
    }
  }
}
```

**Анализ:**
- ✅ **РАЗРЕШЕНО**: Под создан успешно
- 🚨 **КРИТИЧНО**: 
  - Использует созданный SA "monitoring" для выполнения операций
  - Образ Alpine с командой sleep - типичный паттерн для получения shell доступа
  - Длительное время выполнения (3600 сек) указывает на планируемые операции
- 📍 **Корреляция**: Шаг 3 скрипта - создание пода для атаки

### 1.4 Попытка несанкционированного доступа к секретам kube-system

**Событие отказа в доступе:**
```json
{
  "verb": "list",
  "user": {"username": "system:serviceaccount:secure-ops:monitoring"},
  "objectRef": {"resource": "secrets", "namespace": "kube-system"},
  "responseStatus": {"code": 403, "reason": "Forbidden"},
  "annotations": {
    "authorization.k8s.io/decision": "forbid",
    "authorization.k8s.io/reason": "RBAC: access denied"
  }
}
```

**Анализ:**
- ❌ **ЗАБЛОКИРОВАНО**: RBAC корректно заблокировал доступ
- 🚨 **КРИТИЧНО**: Попытка доступа к секретам системного namespace
- 💡 **ЗАЩИТА СРАБОТАЛА**: Система безопасности предотвратила компрометацию критических секретов
- 📍 **Корреляция**: Шаг 4 скрипта - `kubectl --as=system:serviceaccount:secure-ops:monitoring get secrets -n kube-system`

### 1.5 Создание привилегированного пода "privileged-pod"

**Событие создания:**
```json
{
  "verb": "create",
  "objectRef": {"resource": "pods", "namespace": "secure-ops", "name": "privileged-pod"},
  "requestObject": {
    "spec": {
      "containers": [{
        "name": "pwn",
        "image": "alpine",
        "securityContext": {"privileged": true}
      }]
    }
  },
  "responseStatus": {"code": 201}
}
```

**Анализ:**
- ✅ **РАЗРЕШЕНО**: Под с привилегированным контекстом создан
- 🚨 **КРАЙНЕ КРИТИЧНО**:
  - `privileged: true` дает полный доступ к хост-системе
  - Контейнер "pwn" (от "pwned") - явно вредоносное название
  - Может использоваться для escape из контейнера и компрометации ноды
- 📍 **Корреляция**: Шаг 5 скрипта - создание привилегированного пода

### 1.6 Попытка латерального движения к системным подам

**Событие листинга системных подов:**
```json
{
  "verb": "list",
  "objectRef": {"resource": "pods", "namespace": "kube-system"},
  "user": {"username": "minikube-user"},
  "responseStatus": {"code": 200}
}
```

**Анализ:**
- ✅ **РАЗРЕШЕНО**: Пользователь с правами masters может просматривать системные поды
- 🚨 **ПОДОЗРИТЕЛЬНО**: Разведка системных компонентов для планирования атаки
- 📍 **Корреляция**: Шаг 6 скрипта - поиск целей для латерального движения

### 1.7 ЭСКАЛАЦИЯ ПРИВИЛЕГИЙ - Создание RoleBinding с cluster-admin

**Критическое событие:**
```json
{
  "verb": "create",
  "objectRef": {"resource": "rolebindings", "namespace": "secure-ops", "name": "escalate-binding"},
  "requestObject": {
    "roleRef": {"kind": "ClusterRole", "name": "cluster-admin"},
    "subjects": [{"kind": "ServiceAccount", "name": "monitoring", "namespace": "secure-ops"}]
  },
  "responseStatus": {"code": 201}
}
```

**Анализ:**
- ✅ **РАЗРЕШЕНО**: RoleBinding создан успешно
- 🚨 **МАКСИМАЛЬНО КРИТИЧНО**:
  - Service Account "monitoring" получил права `cluster-admin`
  - Полная эскалация привилегий - теперь SA может выполнять любые операции в кластере
  - Нарушение принципа минимальных привилегий
- 📍 **Корреляция**: Шаг 9 скрипта - финальная эскалация привилегий

## 5. РЕКОМЕНДАЦИИ ПО БЕЗОПАСНОСТИ

### 5.1 Немедленные действия:
1. **Удалить скомпрометированные ресурсы**:
   ```bash
   kubectl delete namespace secure-ops
   kubectl delete rolebinding escalate-binding -n secure-ops
   ```

2. **Проверить активные сессии** service account "monitoring"

3. **Аудит всех RoleBindings** с cluster-admin правами

### 5.2 Долгосрочные меры:
1. **Pod Security Standards**: Внедрить политики, запрещающие privileged контейнеры
2. **Admission Controllers**: Настроить контроллеры для блокировки подозрительных операций
3. **RBAC аудит**: Регулярная проверка привилегий service accounts
4. **Мониторинг в реальном времени**: Настроить алерты на:
   - Создание privileged подов
   - Эскалацию привилегий
   - Доступ к системным namespace

### 5.3 Политики безопасности:
```yaml
# Пример Pod Security Policy
apiVersion: policy/v1beta1
kind: PodSecurityPolicy
metadata:
  name: restricted
spec:
  privileged: false  # Запретить privileged контейнеры
  allowPrivilegeEscalation: false
  requiredDropCapabilities:
    - ALL
```

**Ключевые выводы:**

- Отсутствие контроля на создание привилегированных подов критично
- Эскалация привилегий через RoleBinding представляет максимальную угрозу
- Аудит-логи предоставляют полную картину инцидента для расследования

**Статус безопасности:** 🚨 **КРИТИЧЕСКИЙ** - кластер был полностью скомпрометирован через эскалацию привилегий.

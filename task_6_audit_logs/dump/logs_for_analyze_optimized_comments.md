# Подробный анализ 13 событий аудита Kubernetes

Проанализирую каждое из 13 событий в логах аудита:

## **Событие 1-2, 9-13: Обновления Endpoints от Storage Provisioner**
**Тип:** Системная активность  
**Пользователь:** `system:serviceaccount:kube-system:storage-provisioner`  
**Действие:** UPDATE на `/api/v1/namespaces/kube-system/endpoints/k8s.io-minikube-hostpath`

**Комментарий:** Штатная работа системного компонента minikube для управления хранилищем. Storage provisioner регулярно обновляет endpoints для hostpath provisioner. Эти события повторяются каждые ~2 секунды (timestamps: 13:05:11, 13:05:13, 13:05:15, 13:05:17, 13:05:19, 13:05:21, 13:05:23), что является нормальным поведением для поддержания актуальности endpoints.

---

## **Событие 3: Создание namespace "secure-ops"**
**Тип:** Административное действие  
**Пользователь:** `minikube-user` (группа `system:masters`)  
**Действие:** CREATE namespace `secure-ops`  
**Уровень аудита:** RequestResponse

**Комментарий:** **🔴 КРИТИЧЕСКОЕ СОБЫТИЕ** - Создание нового namespace с подозрительным названием "secure-ops". Пользователь с правами cluster-admin создает новое пространство имен, что может быть началом атаки или несанкционированной деятельности. Требует немедленного расследования.

---

## **Событие 4: Автоматическое создание ConfigMap**
**Тип:** Системная активность  
**Пользователь:** `system:serviceaccount:kube-system:root-ca-cert-publisher`  
**Действие:** CREATE configmap `kube-root-ca.crt` в namespace `secure-ops`

**Комментарий:** Автоматическое создание корневого CA сертификата в новом namespace. Это штатное поведение Kubernetes - при создании нового namespace автоматически добавляется ConfigMap с корневым сертификатом для доступа к API.

---

## **Событие 5: Создание подозрительного Pod "attacker-pod"**
**Тип:** Потенциально вредоносная активность  
**Пользователь:** `minikube-user` (группа `system:masters`)  
**Действие:** CREATE pod `attacker-pod` в namespace `secure-ops`  
**Уровень аудита:** RequestResponse

**Комментарий:** **🔴 КРИТИЧЕСКОЕ СОБЫТИЕ** - Создание Pod с явно подозрительным именем "attacker-pod" на базе Alpine Linux с командой `sleep 3600`. Это классический паттерн для создания долгоживущего контейнера для последующих атак. Pod использует default service account и имеет доступ к Kubernetes API через mounted token.

---

## **Событие 6: Успешный доступ к секретам kube-system**
**Тип:** Доступ к критическим данным  
**Пользователь:** `minikube-user` (группа `system:masters`)  
**Действие:** LIST secrets в namespace `kube-system`  
**Уровень аудита:** Request

**Комментарий:** **🟡 ПОДОЗРИТЕЛЬНОЕ СОБЫТИЕ** - Администратор получает список всех секретов в системном namespace kube-system. Это может быть разведкой перед атакой или штатным администрированием. Требует контекстного анализа.

---

## **Событие 7: Блокированная попытка доступа к секретам**
**Тип:** Заблокированная атака  
**Пользователь:** `minikube-user` с impersonation `system:serviceaccount:secure-ops:monitoring`  
**Действие:** LIST secrets в namespace `kube-system` (ЗАБЛОКИРОВАНО)  
**Результат:** HTTP 403 Forbidden

**Комментарий:** **🔴 КРИТИЧЕСКОЕ СОБЫТИЕ** - Попытка эскалации привилегий через impersonation. Администратор пытается выполнить действие от имени service account `monitoring` из namespace `secure-ops` для доступа к секретам kube-system. Это классическая техника атаки для обхода RBAC. Система корректно заблокировала попытку.

---

## **Событие 8: Создание привилегированного Pod**
**Тип:** Критическая угроза безопасности  
**Пользователь:** `minikube-user` (группа `system:masters`)  
**Действие:** CREATE pod `privileged-pod` в namespace `secure-ops`  
**Уровень аудита:** RequestResponse

**Комментарий:** **🔴 КРИТИЧЕСКОЕ СОБЫТИЕ** - Создание Pod с привилегированным контейнером (`"privileged": true`). Привилегированные контейнеры имеют полный доступ к хост-системе, что является серьезной угрозой безопасности. Контейнер назван "pwn" (сленг хакеров для "взлом"), что явно указывает на злонамеренные цели.

---
